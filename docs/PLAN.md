## 2. Architecture

```
  Cnam GPU server or local Ollama / Gemini / Claude APIs
          │ (LLM calls; keys from .env or GUI, never written to YAML/logs/exports)
  ┌───────┴─────────────────────────────── host (.venv) ───────────────────────────┐
  │  GUI backend (FastAPI + WebSocket)  ──  job manager (capture, oracle, training) │
  │  Campaign orchestrator: task generator · operator agent · red-team agent        │
  │  (same client code, same agent identity, same pacing → no timing side channel) │
  └───────┬──────────────────────────────────────────────────────────────────────┬─┘
          │ north network 10.77.1.0/24 (not captured)                             │
  ┌───────┴────────────────────┐                                                  │
  │ Edge IIoT gateway 10.77.1.10│  six tools · static allow-list per task type    │
  │  northbound HTTP JSON tools │  log of every call with task ID                 │
  │  monitor (graph + scorer)   │  scores each write before forwarding (no block) │
  └───────┬────────────────────┘                                                  │
          │ cell network 10.77.2.0/24 — captured (tcpdump → flows + Modbus)        │
   ┌──────┼───────────┬────────────┬──────────────┬──────────────┐                │
   │gateway .10   HMI .20      EWS .30     PLC_MIX .101  PLC_COAT .102  PLC_SLIT .103
   │              1 Hz polls   diag. reads  OpenPLC v4    OpenPLC v4     OpenPLC v4
   └─────────────────────────────────────────┬──────────────┬──────────────┬───────┘
                                field network 10.77.3.0/24 (remote I/O, not captured)
                                             └──────── process simulator .50 ┘
                                                 (plant physics, 10 Hz, seeded)
  Oracle-only (outside the monitor's inputs): twin = same physics + same compiled ST
  logic, replayed offline; operating limits; recipes; ground truth; plant state.
```

* **Purdue-style separation.** The cell network (level 2) is what the monitor sees: the
  gateway log, the Modbus transactions, the flow records, and 1 Hz PLC tag values
  (§III-B). The field network (PLC ↔ remote I/O) is not captured, as in a real plant where
  the I/O bus is a separate segment. The north network keeps agent HTTP traffic out of the
  cell capture.
* **Twin.** The live simulator and the oracle twin are the same Python physics code. The
  twin couples it, in lockstep at the PLC scan period (100 ms), to the three PLC programs
  compiled by STruC++ from the very `.st` files that run on OpenPLC. Noise is counter-based
  (keyed by seed, signal and tick), so removing a command does not change the noise.
  After each capture, a **fidelity check** replays the unmodified command log and reports
  the error between replayed and logged tags. The oracle is only trusted if this error is
  small (threshold in the config).
* **Monitor view.** One loader (`graphiot.data.monitor_view`) is the only way the graph
  builder and all detectors read data. It opens a whitelist of files and columns. Recipes,
  operating limits, twin outputs, ground truth and LLM logs live in other directories and
  are never opened by it. Automated tests enforce this (§5).

### 2.1 Testbed options (light, real OpenPLC, real Modbus TCP)

1. **Docker Compose (target).** One container per PLC from the official OpenPLC Runtime
   v4 image (pinned by digest at first pull), three bridge networks with fixed IPs, one
   shared Python image for gateway/HMI/EWS/simulator, and a capture container in the host
   network namespace that runs `tcpdump` on the cell bridge (named `gi-cell`). No GNS3, no
   VMs, no pfSense.
2. **Dev backend (development and CI only).** The same compiled ST logic, served over real
   Modbus TCP by a small Python process per PLC, on loopback addresses `127.77.x.y` (one IP
   per component, no root needed). Without root there is no packet capture, so flows are
   **synthesized** from the components' own transaction logs. Every run records
   `plc_backend` and `flow_source`. The GUI shows a red banner on dev runs, and the result
   export refuses dev runs unless forced. **No paper number may come from the dev backend.**

### Pilot path (what runs first)

1. You resolve Q1 (Docker group) → `./start.sh` → Experiment tab → load `configs/pilot.yaml`
   → *Start testbed* (pulls the OpenPLC v4 image once, deploys the three programs).
2. *Start campaign*: 1 h benign operation with ~30 red-team takeovers at random times
   (Poisson schedule, seeded). Unattended; ~2.5–3 h wall-clock.
3. *Run oracle* (primary; fallback if the fidelity check fails) → *Pilot go/no-go*:
   context-shifted count (≥ 50), depth-3 tree AUPRC (< 0.9) on triple + phase + task type
   with a chronological split, B0 AUPRC. The table goes to Results with its CSV/LaTeX.
4. If the tree exceeds 0.9: one revision of the red-team prompt and task generator
   (versioned in the config), as the paper allows, then a second pilot.

Until Q1 is solved, the same pipeline runs on the dev backend for testing only.

## 5. Tests required by the task (all in `tests/`)

* **Causal rule** — perturbing any event with timestamp ≥ t (including the command's own
  effect on tags) leaves the score of a command at t unchanged; perturbing events < t
  changes it. Run for the GNN and for every baseline that uses context.
* **No leakage of recipes / limits / twin outputs** — (a) the monitor-view loader exposes
  no forbidden file or column; (b) a file-access audit during graph building and scoring
  fails if a forbidden path is opened; (c) metamorphic test: rewriting recipes, limits and
  twin outputs leaves every graph feature and score bit-identical.
* **Chronological splits** — train < val < test in time; 70/10/20 of benign time; every
  red-team episode is in test; thresholds and hyperparameters are fitted without red-team
  data.
* **Oracle labels** — synthetic episodes with a known violation and a known culprit command;
  τ and T_min boundary cases; fallback 120 s rule.
* **Checkpoint resume** — interrupt training, resume from the checkpoint, and get weights
  identical to an uninterrupted run (CPU, deterministic kernels).

## 6. Open questions (your decisions)

Blocking items first. Each has the default the code uses until you answer.

**Blocking**

* **Q1 — Docker access.** Please run once: `sudo usermod -aG docker $USER`, then log out and
  back in (or reboot). Without it, the real OpenPLC testbed cannot start. *Default:*
  dev backend for development only.
* **Q2 — Disk space.** 8.5 GB free. May I clear `~/.cache/pip` (5.5 GB) and `~/.npm`
  (2.5 GB)? They are caches and are rebuilt on demand. *Default:* I do not touch them; the
  venv uses uv's cache in place.
* **Q3 — Which oracle was pre-registered?** The paper says the choice was due on 17/10 and
  the OSF registration on 22/10. Was it filed, and with which oracle (primary twin replay
  or fallback), which outputs, limits, τ and T_min? The code needs these values as they
  were registered. *Default:* primary oracle, τ = 0.05, T_min = 10 s, limits from
  `plant/operating_limits.yaml` (my proposal in PROCESS_DESIGN.md). If a registration
  exists with other values, the config must take them, not mine.
* **Q4 — OpenPLC runtime version.** v4.3.1 (current, maintained, same compiler as the twin;
  needs our headless `program.zip` packaging) or v3 (archived, uploads `.st` directly, used
  by your earlier BATTwin dataset?). *Default:* **v4**. The ST code stays compatible with
  both (conservative IEC subset).

**Methodology (the paper is ambiguous or seems inconsistent)**

* **Q5 — B3 E-GraphSAGE needs attack labels.** It is a supervised classifier, but the
  protocol has no labelled attacks outside the test set. Options: (a) train it on the
  **pilot** campaign's labelled data (disjoint from the main campaign; this gives B3 *more*
  information than our model, a conservative comparison); (b) use Anomal-E (same authors,
  self-supervised E-GraphSAGE, public code); (c) both. *Default:* (a), recorded in
  DEVIATIONS.md.
* **Q6 — B4 AIRGuard outputs decisions, not scores.** AUROC/AUPRC need a score. If it has
  no continuous risk score, we report recall and FPR at its single operating point and mark
  AUROC as n/a. *Default:* that.
* **Q7 — B0 unseen-bin score.** §V-E: "score 1 if the bin is unseen, else the bin's
  negative log-frequency". Seen bins with frequency < e⁻¹ ≈ 0.37 then score *above* unseen
  bins, which ranks unseen values as less surprising than rare seen ones. Looks like a
  typo. Proposal: unseen → +∞ (ranked above every seen bin). *Default:* the proposal,
  switchable to the literal text in the config (`b0.unseen_score: literal|max`).
* **Q8 — Context-shifted slice and open-ended bins.** With Q = 8 quantile bins, the first
  and last bins are open-ended, so an extreme value (far outside benign data) falls in a
  bin that occurs in benign data and can count as context-shifted. Add "value within the
  benign training range of the tag" to Definition 1? *Default:* paper's definition; the
  stricter variant is reported as a diagnostic count.
* **Q9 — Over-determined harmful episodes.** §V-B: "a command is harmful if removing it and
  replaying brings all outputs back inside their limits". If two commands each cause the
  violation alone, neither is labelled harmful. *Default:* the paper's rule; the count of
  harmful episodes with zero harmful commands is reported in the pilot table.
* **Q10 — "Back inside their limits".** Interpreted as "the episode criterion (≥ τ for
  ≥ T_min) is no longer met" (symmetric with the episode label), not "zero exceedance".
  *Default:* that; `oracle.command_rule: episode_criterion|strict`.
* **Q11 — Host role of PLC endpoints.** Flows (Host→Host) mostly end at PLCs, but Table II
  lists host roles HMI, EWS, gateway, unknown. *Default:* add the role value `plc` for PLC
  network endpoints (one extra one-hot entry; no new node or edge type).
* **Q12 — Confidence intervals.** Table III's caption says "95 % CI over 3 seeds"; §V-F
  says "bootstrap over episodes". *Default:* bootstrap over episodes, averaging the 3 seeds
  inside each resample.
* **Q13 — McNemar with 3 seeds.** Per seed (3 tests) or on the majority vote of the 3 seeds
  per episode? *Default:* majority vote as the pre-registered test, per-seed tests reported
  as robustness.
* **Q14 — Episode-level slices.** *Default:* an episode is in slice S if it is harmful and
  contains ≥ 1 command of S; it is detected if the detector alarms on ≥ 1 command of S in
  it, where S = all commands (All), commands that passed the allow-list (Allow), or
  context-shifted commands (Ctx). This gives B1 = 0 on Allow and Ctx, as in Table III.
* **Q15 — Red-team takeover point and length.** *Default:* the red team takes over at the
  start of a randomly chosen task (inherits its task ID) and acts for at most 8 min or until
  it stops; then the operator resumes with the next task.
* **Q16 — Benign time after an attack.** Operator time right after a red-team episode
  carries the attack's after-effects. *Default:* paper's literal split (only the episode
  interval is removed); `splits.exclude_after_redteam_s` (default 0) can remove a recovery
  margin.
* **Q17 — Timing side channel.** Agent features include the tool-call rate. A fast API red
  team vs a slow local operator would be detectable by speed alone. *Default:* both agents
  share the same client and the same pacing (a random think time drawn from one
  distribution, floor above both LLMs' latency). Reported as a threat to validity.
* **Q18 — Models.** Operator: open-weight 7–8B (paper). Red team: different family.
  *Default:* operator `llama3.1:8b` (Meta) via Ollama; red team `qwen2.5` 7B (Alibaba) via
  Ollama. Gemini or Claude if you prefer an API model (needs a key).
* **Q19 — Interpretations I will use unless you object:** a "batch of 32 snapshots" is
  truncated BPTT over 32 consecutive snapshots; quantile bins are fitted per tag on benign
  training write values (fallback to the 1 Hz tag series below 2·Q distinct writes);
  `load recipe` expands to one scored command per written tag; "alarms per hour" counts
  alarmed benign test commands per benign test hour; in the attacker, every edit costs the
  number of events it adds and a time shift costs 1.

**Paper text that will need an update (no methodology change)**

* §V-A: "OpenPLC, Modbus TCP, GNS3, pfSense" → Docker Compose testbed with OpenPLC Runtime
  v4 (see DEVIATIONS.md D1).
* §III-A: PLCs expose coils and holding registers *and* input registers (sensors from
  remote I/O).

## 7. Risks

* **Real stack untested until Q1.** The Compose file and the OpenPLC v4 deployment code are
  written against the runtime's documented REST API and config schemas, but cannot be run
  here. Expect a short debugging session when Docker access works.
* **Twin fidelity.** Live PLC scans and the simulator are not synchronised (≤ 1 scan of
  jitter). The fidelity check quantifies it per capture.
* **LLM speed on CPU.** Local 8B models answer in 10–60 s on this laptop. For the pilot,
  point Ollama to the GPU server (`llm.ollama.base_url`).
* **Red-team refusals.** API models may refuse red-team instructions. Refusals are logged;
  an episode without effect is labelled benign by the oracle, as the paper says.
